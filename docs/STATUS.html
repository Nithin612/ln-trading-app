Part I
The system, end to end

What the platform is and how every layer fits together — architecture, the signal engine, the Rust core, realtime, data, and the rules that bind them. This part describes how it works and changes only when the system does.

01 · What this is

What this is, in one paragraph

A personal intelligent stock-suggestion and algo-trading platform for the Indian markets (NSE/BSE). It ingests market data — end-of-day and live tick-by-tick — runs every stock through a weighted confluence signal engine that only fires when 5–7 independent technical factors agree at the same price level, sizes each idea off a mandatory stop-loss rule, and surfaces the result as an actionable suggestion: entry, stop, target, quantity, and why.

Trades execute in paper mode today; live order placement is gated behind an explicit opt-in plus a proven profitable paper record. Built solo, for personal use first, with the option to productise later.

Guiding principle

Profits can't be promised, but losses are controlled by construction — mandatory sizing, max-SL rejection, class-correct validity, and a non-disableable circuit breaker.

02 · Two eras

The two eras: v1 and the v2 upgrade

v1 (2025 → mid-2026, complete). Phases 0–11 built the whole vertical: auth, stock master, a 50-filter screener, category tagging, EOD ingestion (OHLCV + FII/DII + bulk/block deals), the 14-factor confluence engine, a dashboard, Kite WebSocket plumbing, paper trading with a circuit breaker, a strategy lab, a journal, and portfolio import. It worked — but a deep adversarial review found the "live" pipeline had never worked end-to-end (four integration bugs), position sizing was 100× too small, and the code had quietly drifted from the signal spec. v1 Phase 12 (live trading) was never started.

v2 (current — approved 2026-07-03). Not a rewrite — a foundation repair plus upgrade: a Rust compute core, an honest tick-to-tick realtime layer, four data-driven trading-style engines, F&O capability, a UI overhaul, outcome tracking, then finally live trading. The old v1 Phase 12 became v2 Phase 7. Phases 0–5 are closed and Phase 6 is built; the strip below is the whole journey.

Process model

Four long-lived processes plus two datastores: FastAPI (REST + WS fanout) · live-worker (KiteTicker + embedded Rust LiveEngine; restarts daily at token expiry with warmup + gap-fill) · Celery worker + beat (EOD ingestion, nightly signals, expiry sweeps, the pair-signal mint) · Postgres + Redis. The tick hot path is deliberately boring concurrency: ticker thread → queue.Queue → consumer thread → one PyO3 call per tick batch → sync redis pipeline. No asyncio in the hot path — two of v1's four live bugs were asyncio/thread impedance.

05 · Signal engine

The signal engine — our edge

docs/SIGNAL_ENGINE.md is the protected spec — the heart of the whole system, hook-guarded, changed only by explicit instruction plus a §8 backtest regression.

The philosophy: confluence, not single indicators

A signal is multiple independent indicators agreeing at the same price level. "RSI < 30, buy!" is noise — it is why most retail traders lose. The edge is requiring 5–7 conditions to align; it is the formalisation of the masterclass Double Confirmation (DC1/DC2) principle. Every signal carries four parts: direction (BUY/SELL), classification, levels (entry, SL, TP, qty), and justification (which factors fired, their scores, the confidence %).

The 14-factor universe

Each factor returns a score from −1.0 (strongly bearish) to +1.0 (strongly bullish); 0.0 means "not applicable" and is excluded from the weight denominator.

GroupFactorsNotes
Single-candle patternsMarubozu, Doji, Hammer, Hanging Man, Shooting Star, Paper UmbrellaContext-aware — a hammer at support scores; mid-trend it doesn't
Multi-candle patternsEngulfing, Harami, Piercing/Dark Cloud, Morning/Evening StarStar requires a full-body gap (canon G)
IndicatorsRSI, RSI divergence, MACD, MACD histogram, EMA cross, price vs EMA, Multibagger EMA, ADX+DI, Bollinger, Volumepandas-ta reference, ported to Rust
Trend (Dow)Higher-highs/higher-lows via pivots (N=3 intraday, N=5 daily)The macro context — heaviest weight

FibonacciBounces from 0.5 / 0.618 / 0.786 retracements

The confluence scorer

# weighted average of only the factors that actually scored
total_weighted = sum(f.weight * f.score for f in factors)
total_weight   = sum(f.weight for f in factors if f.score != 0)
normalized     = total_weighted / total_weight        # -1 .. +1
confidence_pct = int(abs(normalized) * 100)           # int() truncation is canon
if confidence_pct < 70: return None            # the gate
direction = "BUY" if normalized > 0 else "SELL"
Weight semantics — canon H

Every factor carries its own weight independently; the denominator is the sum of weights of factors that actually scored. So four factors firing decisively beats fourteen firing weakly. Sharing group weights was measured to loosen the gate badly (~400 extra weak trades) and rejected.

ADX regime adjustments: ADX < 20 (weak trend) → require +5% extra confidence; ADX > 40 (strong trend) → threshold drops to 65%. ATR(14) > 3% of price (volatile) → reduce position size 25% (a risk rule, not an alpha rule).

Worked example — real engine output

POWERGRID, 1d. Four factors fired: Bullish Engulfing (+13.50), RSI rising (+6.00), at-support (+8.50), Fib 0.5 bounce (+2.00) = +30.00 over applicable weight 40 → 0.75 → 75% BUY.

Entry ₹288.20 · SL ₹278.40 (last swing low, 3.4% — inside the 8% swing cap) · TP ₹305.49 (6% RRBO target) · qty 1020 at ₹5L capital / 2% risk. Output: "Buy POWERGRID — Bullish Engulfing at support, RSI rising, 75% confidence."

Classification, validity, sizing

  • Classification by strongest-contributing timeframe: 1m/5m → scalp · 15m/1h → intraday · 1d → swing · 1d+Multibagger or 1w → positional.
  • Validity: scalp 30 min · intraday until 3:15 PM IST · swing 5 trading days · positional 30 trading days. Trading-day arithmetic uses the NSE holiday calendar — calendar-day math is a bug. An expiry sweeper runs every 5 minutes.
  • Sizing (mandatory): qty = floor(capital × risk% / |entry − SL|). risk_pct is a whole percent (2.0 = 2%). Reject, never clamp: if the natural SL exceeds the class cap (scalp/intraday 0.5%, swing 8%), the signal is rejected.
  • Trailing stop: at first target close 50% and move SL to breakeven; at the next 6% target book 25% more and trail again. Per-user, an absolute-₹ profit-lock ladder can replace the fixed trail.
06 · Rust core

The Rust compute core

The engine/ Cargo workspace, added in v2, is the platform's compute heart. Three crates: engine-core (pure logic — no I/O, no clocks: indicators, pattern detectors, pivots/Dow/S&R/Fib, the confluence scorer, the risk sizer, the Rayon-parallel backtest, Black-Scholes options math) · engine-py (the PyO3/maturin wheel tradecore) · engine-cli (native replay/bench binary).

Why Rust. The honest bottleneck was never the tick path (500 instruments ≈ 500–2000 ticks/s is trivial) — it was the backtest/tuning loop: the pandas engine recomputed full-window indicators per candle (O(n²)), and weight-grid / walk-forward searches over minute data were infeasible in Python. Reusing the same compiled engine live then eliminates the entire class of live-vs-backtest drift bugs v1 exhibited.

Parity is sacred — the migration contract

The Python analysis/ code is frozen (bugfix-only). Committed golden fixtures generated from it are the oracle. Tolerances are tiered: 1e-9 (EMA family), 1e-6 (Wilder family), and exact equality on factor scores, confidence integers, and signal decisions. A live shadow week ran Rust-decides / Python-double-checks with zero decision diffs (14 clean days). Money is i64 scaled 1e-4, indicators are f64, "not applicable" is Option::None never a 0.0 sentinel.

07 · Realtime

The realtime layer — committed vs forming

Phase 3's core idea: two deliberately distinct output layers, separated at the type level so provisional data can never contaminate real decisions.

LayerWhenGuaranteesTransport
CommittedCandle-close onlySpec-exact, no repainting, backtestable, idempotent · at most once per (tf, period)In-process Rust (µs)
Forming / liveTick-to-tick, 2–4 HzLabelled "forming" · never enters backtests or P&LRedis Streams (durable) + pub/sub (droppable)

The forming layer surfaces entry-zone touches, PDH/PDL and S/R breakout crosses, SL/TP proximity for open positions, volume bursts, provisional confidence on the forming candle, and per-style leaderboard re-ranks.

The tick pipeline

KiteTicker thread → bounded queue.Queue → consumer thread
  → ONE tradecore.LiveBook call per tick batch
  → sync redis pipeline: SET ltp:{stock_id} + PUBLISH ltp/candle + XADD alerts
Committed candles → blocking writer queue → writer thread → Postgres upsert
  → Celery trigger fires AFTER the commit

Backpressure: drop-oldest for LTP-class data, never a candle-closing tick. Session guard in-engine: ticks before 9:15 / at-or-after 15:30 / with non-positive price are rejected and counted, never minted. Daily token expiry (~6 AM IST) is a normal lifecycle event — restart + warmup + gap-fill, not an error loop.

Latency budget — MET

tick → Redis publish p99 ≤ 50 ms at full universe (~2,055 instruments) — met across two full sessions. A record/replay harness proves byte-identical event streams across four full-day soak recordings; replay tests run in CI. These two facts are the realtime exit criteria — Phase 3 was gated on them 2026-08-14.

08 · Paper & risk

Paper trading, risk, and the road to live

Paper mode is the default and the only path today. place_order is paper-only — there is no Kite order/GTT path yet (that is Phase 7). The risk machinery that controls losses by construction:

  • Mandatory position sizing off SL distance, risk-first from the actual fill so a chased fill shrinks quantity instead of over-risking.
  • Max-SL rejection — signals whose natural SL exceeds the class cap are rejected, not clamped.
  • Honest fills — gap-through exits book the gapped market price, not the stop; the fill candle is checked intrabar; SL is checked before TP. Adverse slippage on by default (2 bps); Zerodha round-trip charges modelled so P&L is net.
  • The daily-loss circuit breaker — never disableable, never weakened, never configurable-off.
  • Exit governance (per-user): a fixed trail-SL ladder, or an absolute-₹ profit-lock ladder (breakeven at +₹2k, seal peak−₹1k above ₹3k, ATR room).

The go-live gate. Live trading requires explicit opt-in and a 30-day profitable paper record, enforced in code. The paper clock restarts whenever the fill model changes (a reset endpoint + users.paper_clock_started_at exist for this). Phase 6/7 will replace "30 calendar days" with "N trades across ≥2 regimes, positive expectancy, bounded drawdown".

Honesty note

No system guarantees profits. The truthful adjudicated baseline on 2023–26 daily data is negative — the old flattering +P&L was fill-flattery. Profitability is the job of the Phase-2 profiles (the rrbo swing profile walk-forwards positive: +41.3% / +1.97 Sharpe) and Phase-6 selection tuning (the regime gate, now active), measured against reality.

10 · Data model

Data model & the load-bearing contracts

Postgres + TimescaleDB (:5433). Two data shapes in one database: relational (users, signals, orders, positions, journals) and time-series (OHLCV hypertables). Key tables: ohlcv_1m/5m/15m/1h/1d · option_chain_snapshots · fo_bhavcopy · india_vix_daily · signals (with a first-class regime column) + signal_outcomes (tick-level first-touch ladder + MFE/MAE) · pair_signals (P6.5, shadow-only) · orders · positions (with peak_price/peak_pnl, exit_price/exit_reason, trail state) · stocks (with CA-quarantine flags) · strategy_profiles (versioned) · market_calendar (NSE holidays).

Money & time discipline

Money is always exact: Decimal in Python, Numeric(12,4) in Postgres, i64 scaled 1e-4 in Rust. Storage is UTC; market logic is IST (the half-hour offset makes date-boundary bugs easy — all datetimes are tz-aware).

11 · Frontend

Frontend

React 19 · TypeScript 6 · Vite 8 · Tailwind 4 (token-driven) · Zustand + TanStack Query. Feature areas under src/features/: dashboard, trading, stocks, screener, strategy, journal, portfolio, analytics, alerts, watchlists, filings, categories, market, broker, golive, styles, profile.

The rules that keep money-rendering honest:

  • Colours are tokens only. Five themes (slate default, midnight, carbon, ocean, daybreak) switched by data-theme. Profit/loss via --color-profit / --color-loss; direction is always glyph + colour (▲/▼), never colour alone.
  • Numbers exclusively through lib/format.ts (Indian grouping, ₹, L/Cr). No toFixed/toLocaleString in features. Numeric columns right-aligned tabular-nums.
  • Tables (the app is mostly tables): sticky opaque headers, zebra rows, skeleton loading, explicit empty/error states. ≥200 rows or live → TanStack Virtual + memoised rows. Live prices flash via PriceCell (250 ms pulse), never a full-row re-render per tick.
  • Live data via useLiveQuotes (WebSocket; no auto-reconnect on 4401); tick updates rAF/interval-batched.
  • Auth: JWT — access 45 min in memory, refresh 7 d httpOnly, rotated each refresh.

14 · Hard constraints

Hard constraints — the non-negotiables

From .claude/rules/trading-domain.md — these override convenience, deadlines, and "just this once":

  1. Confluence only. No signal from a single indicator, ever. ≥70% gate.
  2. No look-ahead. Compute on N, valid from N+1; committed signals from complete candles only; the tick layer never enters backtests.
  3. No repainting. A committed signal's factors are frozen at commit time.
  4. Position sizing mandatory on every signal; risk_pct is a whole percent.
  5. Reject, don't clamp SLs that exceed the class cap.
  6. Validity per classification using the NSE trading-day calendar.
  7. Money = Decimal / Numeric(12,4) / i64·1e-4. Storage UTC, logic IST, all tz-aware.
  8. Paper default; live requires opt-in + 30 profitable paper days. The circuit breaker is never disableable.
  9. Kite discipline: token expiry is a lifecycle event; all REST goes through the shared throttled client (~3 rps).
  10. docs/SIGNAL_ENGINE.md is the edge — protected by a hook; spec changes require explicit instruction + a §8 backtest regression.

The verdict — where the edge is and where it leaks

▲ The edge

  • 80–89 confidence — +0.20R (n=307)
  • Trending ADX ≥ 25 — +0.24R (n=140)
  • Choppy ADX < 20 — +0.12R (n=337)

▼ The leak

  • 70–79 confidence, the bulk — −0.07R (n=434)
  • Transitional ADX 20–25 — −0.10R (n=339)
  • 70–79 × transitional — −0.23R (n=250)

Corpus cohort: Nifty50 daily, 816 decided trades since 2023-09-13, expectancy winsorized at ±10R to kill tiny-SL artifacts. The corpus corrected the noisier live read, which had blamed the choppy regime — choppy is fine at +0.12R; transitional is the real drag.

The nuance that shaped the fix

One cell carries the loss: 70–79 × transitional, n=250 — 31% of the corpus, at −0.23R. But 80–89 × transitional is the single best ranked cell at +0.32R (n=75), so a blanket "skip transitional" gate throws away good trades along with the leak. That is exactly what the §8 walk-forward (§19) had to settle before anything shipped — and it did.

22 · MCE

The Market Context Engine — how we build it

The next build phase. Everything so far is bottom-up: a stock earns a signal on its own chart. The MCE adds top-down context — market regime, sector strength, event risk, and (eventually) fundamentals — as a layer that can veto or scale a signal, never invent one.

The one rule that defines it

Context enters as gates and modifiers, never as additive alpha. News and sentiment carry ~0 reliable directional edge but high veto value — they tell you when not to trade, not what to buy. So the MCE can suppress or downweight a confluence signal; it never adds a point of confidence. It is not a multi-state regime engine — one simple, testable gate at a time, each behaviour-changing move through a §8 backtest, shadow-first. The regime gate (§19) is the template: a reversible overlay, measured before it is trusted.

~40% already exists and is reused, not rebuilt: the reactive event_guard (post-filing 60-min suppression), the F&O data stack (India VIX, PCR, max-pain), and the FII/DII flow factor. The build fills the top-down gaps, in this order:

  1. 1
    Per-stock seasonality flag START HERE
    Monthly return distribution over the existing 5y EOD OHLCV (e.g. "seasonally weak in August, n=18") as a soft context modifier. The one piece needing no new data and no engine change — cheap, genuinely new, and it reports n and refuses to rank thin samples. The natural first slice while the shadow evidence accrues.
  2. 2
    One simple top-down market/sector gate
    Suppress or downweight longs when NIFTY is below its 200-DMA or India VIX is high, plus a sector-relative-strength check on existing sector metadata. Uses data we already ingest. Behaviour-changing → a §8 backtest and sign-off, exactly like the regime gate. NOT a multi-state regime machine — a single gate.
  3. 3
    Proactive pre-event (earnings) blackout
    Suppress new signals N trading days before a known results/event date, scaled by class — you don't want a fresh swing entry the day before earnings. Needs a forward earnings/event-calendar source (today's event_guard is reactive only), so it's gated on wiring that feed.
  4. 4
    Fundamental data layer + quality scores BLOCKED
    A new stock_fundamentals table feeding a fundamental gate/modifier and four closed-form quality scores (Altman Z · DuPont · Graham · Ohlson — greenfield, no look-ahead). Blocked on a data-source decision: NSE publishes no free shares-outstanding feed, so market_cap_cr has never been populated — the keystone that unlocks both the screener's headline filter and every fundamental threshold. Candidate sources: extend filings_consumer to parse BSE/NSE XBRL results, or a paid fundamentals API. A data decision, not a build task.
Recommended sequencing & the honest reason

Seasonality first (unblocked, cheap, real), then the top-down gate (§8, uses existing VIX/sector data). The earnings blackout waits on an event-calendar feed; the fundamentals layer waits on the market_cap source decision. Don't start the fundamentals layer before that source is chosen — it is a half-built dead-end otherwise. And don't rush any of it: the current shadow tracks (regime gate, retune, pairs) need weeks to return verdicts, and that accrual window is the natural time to build the MCE.

23 · Phase 7

Phase 7 — live trading, in detail

The last phase, and the only one that places a real order. It opens defensively — the risk gate is built and pinned before the order path exists, because the exact class of bug that gave v1 four integration defects was a live-order path bolted on ahead of its safety seam.

The gate to even start placing orders

Explicit user opt-in and a 30-day profitable paper record, enforced in code (Phase 6/7 replaces "30 calendar days" with "N trades across ≥2 regimes, positive expectancy, bounded drawdown"). The daily-loss circuit breaker is never disableable. Deployment is a static-IP VPS with a tested client kill-switch.

The build order

  1. 1
    RiskEngine single-gate consolidation SLICE 1
    Test-first, equivalence-pinned: consolidate every pre-trade check (sizing, SL cap, circuit breaker, exposure) behind one gate before any live-order path is written. Closes the caller-side circuit-breaker seam. Studied in docs/NAUTILUS_TRADER_ANALYSIS.md §6 — learned, not vendored (Nautilus is LGPL).
  2. 2
    Broker adapter + execution engine + reconciliation
    A BrokerAdapter port over Kite orders, an order state machine (Denied vs Rejected distinguished), and reconciliation of local vs exchange state on restart. mimalloc is a free allocator win worth taking now. The HFT/colocation/FIX layer is explicitly not copied — wrong tier for retail Kite.
  3. 3
    Exchange-resident protective stops (Kite GTT / SL-M)
    The primary live exit lives at the exchange, not in our process — so a crashed worker can't strand a position. The position monitor becomes a supervisor/reconciler, and each trail ratchet becomes a MODIFY of the exchange-side order. Plus a loud LTP-absence alarm for any open live position (the paper monitor currently skips silently).
  4. 4
    Sector-exposure caps + a single open-risk (heat) number
    Simple caps in the RiskEngine gate — this is the answer to the §17 open-heat risk (49.6% of capital uncapped today). NOT VaR/ES, NOT a rolling correlation matrix; simple caps, revisited only if they prove insufficient.
  5. 5
    Tradeability for the shadow strategies
    This is where pair-trading (§21) becomes tradeable — an overnight short leg needs stock futures (or SLB borrow), which needs this order path. And the defined-risk Iron Condor option-selling profile: sell ATM CE+PE but BUY protective wings → the same theta harvest with a bounded max loss. The naked short strangle as taught is rejected (uncapped tail/gap risk). Both paper-first, event-day blackout, §8 incl. gap-through-SL.
  6. 6
    Corporate-action adjustment of open positions
    Adjust entry/SL/TP/qty through an ex-date so R is preserved. CA quarantine currently covers the selection universe only, not held positions. Fill-model reference: LEAN / Nautilus §4 — a catalog to consult, never a dependency.

Sequence: RiskEngine gate → broker adapter at paper-parity → 30 profitable paper days with the kill-switch tested → a 1-stock live pilot. Live trading is the last thing, guarded by the non-disableable breaker and a paper record that had to be earned.

25 · Guardrails

Invariants that bind everything above

  • ✕Live trading does not exist. The order path is paper-only — no Kite order, no GTT. Every "live" recommendation anywhere in the docs is a Phase-7 design constraint, not a description of something running.
  • ◐The engine is frozen; behaviour changes are overlays + §8. app/analysis/, app/backtest/engine.py and the window canon are bugfix-only, and the committed Rust fixtures are the parity oracle. The regime gate is the first behaviour change to ship — and it did so as a reversible downstream overlay, through a §8 walk-forward and sign-off, with the engine untouched. Every future change (the retune, the MCE gates) follows that same path.
  • ◐Confluence only, ≥70% gate, no look-ahead. No signal from a single indicator; factors compute on candle N and are valid from N+1; committed signals come only from complete candles, and the tick-level layer is labelled provisional and never enters backtests or P&L.
  • ◐Reject, never clamp. A signal whose natural SL exceeds its class cap is rejected, not tightened. Sizing is mandatory on every signal, risk_pct is a whole percent, and paper entries size risk-first from the actual fill so a chased fill shrinks quantity instead of over-risking.
  • ✓The daily-loss circuit breaker is never disableable. Not weakened, not configurable-off, not for tests. Any new risk gate is added alongside it.
  • ✓Shadow means shadow. A shadow signal is measured to outcome but never tradeable — the order path admits status == 'active' only, and every tradeable statistic filters is_shadow IS FALSE. Provenance lives on the immutable is_shadow flag, never on the sweeper-overwritten status.
